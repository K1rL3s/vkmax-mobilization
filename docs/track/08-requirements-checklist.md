Все требования из материалов трека в одном месте, без повторов. Жёсткие требования помечены **[!]**: если их не выполнить, решение не допустят к оценке или потеряют баллы напрямую. Остальное — критерии оценки и рекомендации организаторов. В скобках указан источник:

- `task` — [02-task.md](02-task.md)
- `constr` — [03-constraints.md](03-constraints.md)
- `rec` — [04-recommendations.md](04-recommendations.md)
- `sub` — [05-submission.md](05-submission.md)
- `crit` — [06-criteria.md](06-criteria.md)
- `info` — [07-additional-info.md](07-additional-info.md)
- `web` — [webinar-summary.md](webinar-summary.md)

Шкала по каждому критерию: 0 — не выполнен, 1 — слабо, 2 — частично, 3 — хорошо.

## A. Допуск к оценке

- [ ] **[!]** Решение соответствует треку «Умный город»: управление МКД или жилищные вопросы (constr 1, crit)
- [ ] **[!]** MAX используется как среда реализации и/или взаимодействия с продуктом (constr 2, crit)
- [ ] **[!]** Бот или мини-приложение запускается и отвечает, основной сценарий можно пройти до конца (constr 2, crit)
- [ ] **[!]** Презентация есть (crit)

## B. Платформа и реализация

- [ ] **[!]** Решение сделано как чат-бот или как чат-бот с подключённым мини-приложением. Мини-приложение не работает в отрыве от бота (constr 5)
- [ ] **[!]** Функциональность доступна и в мобильной, и в веб-версии MAX (constr 3, web)
- [ ] **[!]** Сдаётся бот с токеном, который выдали организаторы (task 4, info, web)
- [ ] **[!]** Мини-приложение работает по HTTPS (info, web)
- [ ] Бот работает через вебхуки, а не через long polling (web)
- [ ] Бот и хостинг онлайн весь период проверки, с 30 сентября по 14 октября; лимиты внешних сервисов не кончаются раньше (web)
- [ ] Логика разделена разумно: в чате — короткие диалоги, выбор из нескольких вариантов, статусы и уведомления; в мини-приложении — сложные формы, списки, сравнение и возврат к данным (info)
- [ ] Учтены ограничения MAX: ник бота нельзя изменить, бот не создаёт чаты, бот помнит около 1000 чатов, рекламные рассылки запрещены (constr 11, web)
- [ ] Реализация сверена с актуальной документацией MAX (dev.max.ru/docs) (info)
- [ ] Собственный API не обязателен и сам по себе баллов не даёт (constr 6)

## C. Легальность, безопасность и данные

- [ ] **[!]** Нет закрытых библиотек, частных API и чужого кода без свободной лицензии (constr 7)
- [ ] **[!]** В репозитории нет рабочих токенов, паролей, ключей и других секретов (constr 8, crit)
- [ ] **[!]** Соблюдаются законодательство РФ, правила платформы MAX и правила хакатона (constr 9)
- [ ] **[!]** Если используются тестовые, смоделированные или заранее подготовленные данные вместо реальной интеграции, это явно указано в материалах (constr 10, rec 5, info)
- [ ] Модельные данные помечены и в README, и в самом боте (web)
- [ ] Интеграции не имитируются: указано, какие из них модельные и что нужно для настоящей реализации (info)
- [ ] Используются обезличенные, тестовые или синтетические данные (rec 5, web)
- [ ] Если собираются персональные данные, пользователь даёт согласие на их обработку по 152-ФЗ (web)
- [ ] Учтены ПП РФ № 416 (п. 34–35, порядок и сроки ответа на обращения) и порядок работы с обращениями граждан (info, web)
- [ ] Для данных указаны источник, территория, период и дата актуальности (rec 5, info)
- [ ] Разделены официальные факты, расчёты продукта, рекомендации и допущения (info)
- [ ] Если используется LLM: ответы привязаны к источникам, показано основание, предусмотрен случай, когда надёжного ответа нет, догадка модели не выдаётся за факт (info)
- [ ] Честно указано, где при разработке использовался ИИ (web)
- [ ] Доступ к данным соответствует логике решения, очевидных критичных рисков безопасности нет (crit)

## E. Онлайн-этап: продуктовая оценка (40%)

### E1. Потенциал масштабирования — 35%
- [ ] Названы конкретные регионы, организации и контексты за пределами исходного кейса
- [ ] Направления масштабирования соответствуют логике и возможностям продукта
- [ ] Определены условия адаптации: данные, интеграции, ресурсы, изменения продукта
- [ ] Отделено ядро продукта (проблема, логика сценария, архитектура, модель данных, механика, UI) от переменной части (региональные данные, нормативы, справочники, внешние системы, роли, правила) (rec 6, info)
- [ ] Учтены ограничения и риски масштабирования
- [ ] Предложен реалистичный порядок тиражирования, а не «запустим по всей России»
- [ ] Желательно: оценка TAM/SAM/SOM (web)

### E2. Пользовательская ценность — 25%
- [ ] Определены ЦА и приоритетный сегмент, конкретнее, чем просто «жители» (rec 1, task 1)
- [ ] Описана конкретная и актуальная потребность, например по формуле «[пользователь] в ситуации [контекст] хочет [результат], но [барьер], из-за чего [последствие]» (info)
- [ ] Сформулирован полезный результат для пользователя
- [ ] Показано преимущество перед текущим способом: As Is → To Be, сравнение с конкурентами (info, web)
- [ ] Востребованность подтверждена данными, наблюдениями, интервью или аргументированными допущениями; факты отделены от гипотез (rec 2)

### E3. UX/UI — 20%
- [ ] Основной путь соответствует приоритетному сценарию (rec 3)
- [ ] Последовательность действий понятна без пояснений
- [ ] Ключевые действия, навигацию и элементы легко найти и однозначно понять
- [ ] Интерфейс сообщает о загрузке, результате и ошибке
- [ ] Нет лишних шагов, тупиков и противоречивых переходов

### E4. Обоснованность и целостность — 15%
- [ ] Решение соответствует задаче и выбранной проблеме
- [ ] Прослеживается логика «проблема → механика → результат»; технология выбрана под задачу, а не наоборот (rec 4)
- [ ] Ключевые продуктовые решения и допущения аргументированы
- [ ] Функции согласованы и образуют один продукт
- [ ] Решение реалистично с учётом условий и ограничений; границы MVP определены, включая Won't Have (info)
- [ ] Определён ожидаемый эффект и хотя бы одна метрика для проверки: время, число ручных действий, ошибки, доля завершивших сценарий, повторные обращения (task 6, info)

### E5. Качество презентации — 5%
- [ ] Структура быстро объясняет проблему, решение и результат
- [ ] Ключевые мысли сформулированы ясно
- [ ] Информации достаточно для оценки продукта
- [ ] Схемы, изображения и демо читаемы
- [ ] Слайды не перегружены второстепенным и повторами

## F. Онлайн-этап: техническая оценка (60%)

### F1. Работоспособность и полнота — 30%
- [ ] Основной сценарий проходится от начала до заявленного результата
- [ ] Ключевые функции основного сценария работают
- [ ] Если есть свой API, обязательные проверки проходят

### F2. Интеграция и обмен данными — 20%
- [ ] Компоненты корректно и согласованно взаимодействуют
- [ ] Данные, состояния и результаты обрабатываются предсказуемо
- [ ] Внешние интеграции работают так, как заявлено; поведение совпадает с документацией
- [ ] Если есть свой API, статус-коды, форматы, заголовки и поля соответствуют контракту

### F3. Стабильность и обработка ошибок — 10%
- [ ] Стабильная работа при повторном прохождении сценария
- [ ] Ошибки и некорректный ввод обрабатываются предусмотренным образом
- [ ] После ошибки можно продолжить без полного перезапуска, в том числе при сбое внешнего сервиса
- [ ] Нет систематических сбоев, тайм-аутов и критичных задержек

### F4. Архитектура — 20%
- [ ] Структура логична и соразмерна MVP, без усложнения ради сложности
- [ ] Понятны компоненты, их роли и связи
- [ ] Ключевая логика разделена так, что решение можно поддерживать и развивать
- [ ] Технические решения соответствуют заявленной функциональности

### F5. Безопасность, зависимости, данные — 10%
- [ ] Секретов в коде нет
- [ ] Версии зависимостей зафиксированы
- [ ] Доступ к данным соответствует логике решения
- [ ] Используемые данные и внешние сервисы, включая LLM, описаны
- [ ] Нет очевидных критичных рисков

### F6. Документация и комплектность — 10%
- [ ] Материалы соответствуют зафиксированной версии
- [ ] Решение воспроизводится по инструкции; проверено запуском с нуля на чистом окружении (web)
- [ ] Описаны запуск, архитектура, зависимости, окружение и интеграции
- [ ] Указаны порядок проверки основного сценария и ожидаемый результат
- [ ] Известные ограничения задокументированы

### Бонус за расширенное использование MAX: +0,15 (всё или ничего)
- [ ] Основной сценарий полностью работает
- [ ] Использована возможность MAX сверх минимума, например осмысленная связка бота и мини-приложения или уведомления (web)
- [ ] Эта возможность приносит пользу, органично встроена, работает от начала до конца и описана в материалах
- Собственный API, количество функций и обязательные возможности бонуса не дают
