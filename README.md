# Жэка Коммуналкин

## Команда Мобилизация

Чат-бот с мини-приложением в MAX для жителей многоквартирных домов и их
управляющих компаний. Трек «Умный город».

Бот: https://max.ru/t260_hakaton_max_bot

- [Кирилл Лесовой](https://github.com/K1rL3s) - капитан, бэкенд
- [Даниил Карпенко](https://github.com/wannasleep66) - фронтенд
- [Даниил Неслуховский](https://github.com/nesclass) - аналитик
- [Артаган Мальсагов](https://github.com/ZeN220) - бэкенд

## Назначение

Житель с бытовой проблемой (протечка, лифт, мусор) не знает, кому и как о
ней сообщить, и не видит, что стало с обращением. С 1 сентября 2026 года УК
обязаны работать с жителями через MAX (ПП РФ от 26.01.2026 № 40), но
готового инструмента для этого у большинства УК нет.

Жэка выполняет эту обязанность за УК и дает жителю прозрачный канал:

- **житель** находит свой дом, подает заявку с фото, видит статус и срок,
  получает уведомления, передает показания счетчиков, смотрит начисления,
  карточку дома и голосует в опросах;
- **сотрудник УК** принимает заявки, меняет статусы, назначает
  исполнителей, видит показания и дашборд аналитики по своим домам,
  публикует объявления в домовые чаты.

Один бот обслуживает все организации: у жителя один вход независимо от того,
какая УК управляет его домом.

## Основной сценарий

1. Житель открывает бота и дает согласие на обработку персональных данных.
2. Находит свой дом: город - улица - дом, по геопозиции или по ссылке из
   домового чата.
3. Подает заявку: описание, категория, фото. Сразу получает номер и срок.
   В мини-приложении категорию подсказывает модель по описанию, в боте
   житель выбирает ее кнопкой.
4. Сотрудник УК получает от бота сообщение о новой заявке, принимает ее и
   меняет статус. Житель получает уведомление на каждом шаге, кнопка в
   уведомлении открывает заявку в мини-приложении.
5. Житель подтверждает квартиру и передает показания счетчиков: фото,
   распознанное значение, подтверждение, расход и сравнение со средним по
   дому.
6. Заявка выполнена - житель ставит оценку. Если сделано плохо, подает
   повторную заявку со ссылкой на старую.

Бот ведет короткие диалоги, присылает уведомления и напоминания. Формы,
списки, графики и кабинет УК - в мини-приложении, его открывает кнопка
«📱 Открыть приложение» под меню бота.

## Состав и архитектура

```
MAX ──HTTPS──> TLS на хосте ──> nginx :80 ─┬─ /          ─> web        статика мини-приложения
                                           ├─ /api/      ─> api        FastAPI + бот
                                           ├─ /files/    ─> api        загруженные фото
                                           └─ = /webhook ─> api        вебхук бота

api, worker ──> database (PostgreSQL 16)
            └─> redis (FSM бота, очередь и расписание taskiq)
```

| Сервис | Что делает |
|---|---|
| `web` | Мини-приложение: React + TypeScript, `@maxhub/max-ui`, MAX Bridge. Собирается в статику и отдается nginx внутри образа |
| `api` | FastAPI под gunicorn: REST для мини-приложения и бот на `maxo` в том же процессе, в режиме `polling` или `webhook` |
| `worker` | Фоновые задачи taskiq и их расписание в одном процессе: рассылка уведомлений, сообщения в домовые чаты, заполнение демо-данных, напоминания о показаниях, опросах, поверке и приеме, автозакрытие опросов и приемки |
| `migrations` | Прогоняет миграции alembic и завершается. Он же собирает образ бэкенда для `api` и `worker` |
| `database` | PostgreSQL 16 |
| `redis` | Redis 7 |
| `nginx` | Единственная точка входа, разводит запросы по путям |

Код:

- `backend/zheka/bot` - обработчики бота и диалоги;
- `backend/zheka/api` - REST для мини-приложения;
- `backend/zheka/core` - доменные модели и сервисы, общие для бота и API;
- `backend/zheka/infra` - база данных, клиент MAX, Yandex;
- `backend/zheka/broker` - фоновые задачи и расписание;
- `backend/zheka/seed` - демо-данные;
- `frontend/src` - мини-приложение.

Мини-приложение авторизуется подписанным `initData` из MAX: API проверяет
HMAC на токене бота и отклоняет `initData` старше суток. Для проверки API
без MAX есть тестовый токен, см. «Проверка API». Данные организаций
изолированы фильтром в репозиториях: сотрудник одной УК получает 404 на
заявку другой.

## Запуск

Нужны Docker с Compose v2 и токен бота MAX.

```sh
cp .env.example .env    # затем вписать MAX_TOKEN
docker compose up -d --build
```

Команда собирает образы, прогоняет миграции и поднимает все сервисы. Первый
запуск занимает около минуты, не считая скачивания базовых образов.
Проверка готовности:

```sh
curl http://localhost/api/healthcheck
```

Заполнить пустую базу демо-данными:

```sh
docker compose run --rm api python -m zheka.seed
```

API локально пускает только с подписанной `initData` из MAX. Чтобы проверить
его запросами, впишите в `.env` любой `API_TEST_TOKEN`, например
`API_TEST_TOKEN=local`, пересоздайте `api` командой `docker compose up -d api`
и повторите запросы из «Проверка API» с `http://localhost/api` и
`Authorization: Bearer local`.

Локально бот работает в режиме `polling`: не нужны ни домен, ни сертификат.
Для локального запуска берите отдельный тестовый токен: пока у бота включен
вебхук на проде, long polling с тем же токеном обновлений не получит.

Без настоящего токена, с заглушкой из `.env.example`, поднимается все,
кроме бота: API, документация `/api/docs`, статика мини-приложения,
миграции и заполнение базы работают, а в логе `api` одна строка ERROR о
том, что MAX отверг токен и бот не запущен. В логе `worker` та же ошибка
повторяется на каждое уведомление: без бота их некуда отправить. На проде
в режиме `webhook` такая ошибка валит запуск: gunicorn пишет ERROR с
причиной и перезапускает воркер, а healthcheck не отвечает, пока бот не
поднимется.

Мини-приложение открывается только из MAX: без подписанного `initData` или
тестового токена API отвечает 401. MAX открывает его по HTTPS-адресу из
настроек бота на платформе, поэтому без публичного HTTPS-адреса локальную
сборку в MAX не увидеть. Проверять мини-приложение удобнее на развернутом
боте.

## Окружение

Все переменные в `.env.example` с комментариями. Compose читает `.env` из
корня репозитория.

| Переменная | Обязательна | Назначение |
|---|---|---|
| `MAX_TOKEN` | да | Токен бота MAX |
| `MAX_BOT_MODE` | нет | `polling` (по умолчанию, локально) или `webhook` (прод) |
| `MAX_WEBHOOK_URL` | при `webhook` | Публичный HTTPS-адрес вебхука, `https://<домен>/webhook` |
| `MAX_SECRET_TOKEN` | при `webhook` | Секрет вебхука, сверяется с заголовком `X-Max-Bot-Api-Secret` |
| `DEEPLINK_ORG_REGISTER` | да | Скрытый код регистрации УК: 1-64 символа из латиницы, цифр, `_` и `-` |
| `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` | да | Учетные данные PostgreSQL |
| `POSTGRES_HOST`, `POSTGRES_PORT` | вне Docker | Адрес PostgreSQL для запуска вне Docker, в compose зафиксирован |
| `REDIS_PASSWORD` | да | Пароль Redis |
| `REDIS_HOST`, `REDIS_PORT`, `REDIS_DB` | вне Docker | Адрес Redis для запуска вне Docker, в compose зафиксирован |
| `YANDEX_API_KEY`, `YANDEX_FOLDER_ID` | нет | Yandex Vision OCR и Yandex AI Studio. Без них продукт работает без подсказок |
| `YANDEX_MODEL` | нет | Текстовая модель AI Studio, по умолчанию `yandexgpt-5-lite` |
| `FILES_MAX_SIZE_MB` | нет | Потолок размера загружаемого фото, по умолчанию 10 |
| `FILES_DIR` | нет | Каталог фото для запуска вне Docker, в compose это `/data/files` |
| `API_CORS` | нет | Разрешенные источники через запятую, пусто - все. На проде `https://vkmax.k1rles.ru` |
| `API_TEST_TOKEN` | нет | Тестовый токен для проверки API без MAX, заголовок `Authorization: Bearer <токен>`. Пусто - выключено |
| `API_HOST`, `API_PORT` | нет | Адрес gunicorn для запуска вне Docker, в compose `0.0.0.0:7001` |
| `LOG_LEVEL`, `LOG_FORMAT` | нет | Уровень логов и формат: `PLAIN` локально, `JSON` на проде |
| `NGINX_PORT` | нет | Порт nginx на хосте, по умолчанию 80 |

## Порты

| Порт | Где | Кто |
|---|---|---|
| `80` (`NGINX_PORT`) | хост | nginx, единственный опубликованный порт |
| `7001` | сеть compose | `api` |
| `80` | сеть compose | `web` |
| `5432` | сеть compose | `database` |
| `6379` | сеть compose | `redis` |

HTTPS в репозитории не настроен: nginx слушает только 80. На проде TLS
нужен и для мини-приложения, и для вебхука, причем строго на 443 и с
настоящим сертификатом - самоподписанный сертификат MAX отвергает.

## Зависимости

- Бэкенд: Python 3.12. Основное: maxo, FastAPI, SQLAlchemy, alembic, taskiq,
  dishka.
- Фронтенд: Node 24.21.0. Основное: React, `@maxhub/max-ui`, TanStack Query,
  recharts.
- Инфраструктура: `postgres:16.9-alpine3.22`, `redis:7.4.3-alpine3.21`,
  `nginx:1.27-alpine`.

Версии библиотек зафиксированы в `backend/uv.lock` и
`frontend/pnpm-lock.yaml`, образы Docker - по digest в Dockerfile и
`docker-compose.yml`.

## Внешние сервисы

| Сервис | Зачем | Без него |
|---|---|---|
| MAX Bot API | Бот, уведомления, мини-приложение | Не работает ничего |
| Yandex Vision OCR | Распознавание показания счетчика по фото | Житель вводит показание руками |
| Yandex AI Studio | Подсказка категории заявки по описанию | Житель выбирает категорию кнопками |

Оба сервиса Yandex вызываются из запроса мини-приложения с таймаутом 3
секунды и необязательны. Ключ, который Yandex отверг, выключает подсказки до
перезапуска. Подсказка модели только предлагает категорию: житель видит ее и
может выбрать другую.

Интеграции с ГИС ЖКХ нет, оплаты тоже: платеж в мини-приложении
демонстрационный, деньги не списываются.

## Данные

Что хранится: пользователи MAX и их согласие на обработку персональных
данных (версия и дата), дома, квартиры и лицевые счета, заявки с фото,
показания счетчиков, начисления, опросы, объявления, события для аналитики.

- Согласие запрашивается до выбора дома, со ссылкой на политику обработки
  данных. Без согласия бот и мини-приложение дальше не пускают.
- Персональные данные жителя видит только УК его дома.
- Фото лежат на диске в `backend/content` под UUID-именами. Ссылку на фото
  API подписывает на час и выдает только тем, кому фото положено видеть.
- Данные PostgreSQL и Redis живут в томах `<проект>_zheka-postgres` и
  `<проект>_zheka-redis`, где проект - имя папки репозитория.

### Откуда демо-данные

- **Реальные открытые данные:** дома и управляющие организации - Реформа
  ЖКХ (reformagkh.ru), координаты - © участники OpenStreetMap, лицензия
  ODbL 1.0.
- **Модельные, сгенерированные для демонстрации:** все остальное -
  организации «Демо-УК ...», их жители, начисления, показания, заявки и
  документы. В мини-приложении модельные разделы помечены на экране.
- Подробнее - в `backend/README.md`.

## Тестовые данные

`python -m zheka.seed` заполняет пустую базу за одну транзакцию.
На развернутом боте то же делает команда `/seed` в личке с ботом.

История за полгода заканчивается днем заполнения, а дашборд считает
последние 30 дней, поэтому заполнять базу нужно ближе к проверке. Заполнить
заново можно только после пересоздания базы: `docker compose down -v`, затем
запуск и заполнение.

### Демо-доступ

Выдать «логин жителя» в MAX нельзя: у каждого там свой настоящий аккаунт.
Поэтому роль выдает ссылка в бота с параметром `start`:

```
https://max.ru/t260_hakaton_max_bot?start=demo_resident_1
```

| Параметр | Что выдает |
|---|---|
| `demo_resident_N` | Собственную подтвержденную квартиру в первом доме организации N, с начислениями и показаниями за полгода |
| `demo_staff_N` | Роль сотрудника организации N |
| `demo_admin_N` | Роль администратора организации N |

N от 1 до 5. У каждого проверяющего-жителя своя квартира, поэтому жители не
видят действий друг друга. Сотрудники одной демо-УК видят общие входящие
заявки: для независимой проверки берите разные N. Один аккаунт может пройти
по нескольким ссылкам и получить сразу несколько ролей. Без заполненной базы
ссылка отвечает «Демо-доступ еще не готов».

Демо-УК общие, поэтому их сотрудники видят имена других проверяющих, а сами
проверяющие защищены друг от друга. Заблокировать жителя или снять с него
подтверждение квартиры можно только у модельного жителя. Объявление в личку
из демо-УК приходит только его автору.

В демо-УК заявка становится коллективной, когда об одной проблеме в доме
за сутки сообщают 10 квартир, а не 3, как по умолчанию: иначе заявки
проверяющих из одного демо-дома склеивались бы между собой. Порог меняет
администратор в настройках организации.

У всех квартир лицевой счет - номер квартиры, дополненный нулями до 10
цифр: у кв. 12 это `0000000012`. С ним в мини-приложении можно подтвердить
любую квартиру, а не только демо-квартиру из ссылки. Исключение - квартиры
проверяющих `Д...`: они подтверждены сразу, а их счет случайный, чтобы
чужую демо-квартиру не занял другой проверяющий.

## Сценарий проверки

1. Откройте `https://max.ru/t260_hakaton_max_bot?start=demo_resident_1`.
   Бот попросит согласие на обработку данных, дайте его.
2. Бот сообщит: «🎟 Демо-доступ открыт: ваша квартира ...». Откройте
   приложение кнопкой «📱 Открыть приложение».
3. Во вкладке «Заявки» подайте заявку о протечке: опишите проблему, модель
   подскажет категорию, приложите фото. Заявка появится с номером, статусом
   и сроком.
4. В Профиле откройте карточку дома: УК, тарифы, капремонт, документы.
5. На Главной нажмите «Передать» и передайте показания счетчика: сфотографируйте
   его или приложите любое фото счетчика, значение распознается или вводится
   вручную. Приложение покажет расход и сравнение со средним по дому. Фото
   обязательно: по нему УК разбирает споры о показаниях.
6. Откройте `https://max.ru/t260_hakaton_max_bot?start=demo_staff_1` тем же
   аккаунтом. Бот сообщит: «🎟 Демо-доступ открыт: вы сотрудник ...» и даст
   кнопку «🧑‍💼 Открыть кабинет УК». Сообщение сотрудникам о новой заявке
   автору заявки не приходит: чтобы увидеть его, откройте эту ссылку вторым
   аккаунтом до шага 3.
7. Во вкладке «Заявки» кабинета УК выберите фильтр «Новые» и откройте свою
   заявку: номер виден в строке списка. Примите ее в работу, начните работы
   и отправьте на приемку. Закрывает заявку житель, когда принимает работу,
   иначе она закрывается сама через 48 часов.
8. На каждую смену статуса бот пришлет жителю уведомление с кнопкой
   «📱 Открыть заявку». Когда заявка на приемке, бот пришлет карточку с фото:
   примите работу и поставьте оценку прямо в чате или в приложении. Если
   нажать «👎 Сделано плохо» и написать, что не так, уйдет повторная заявка
   со ссылкой на старую.
9. Во вкладке «Аналитика» кабинета УК - дашборд по домам организации.

## Ожидаемое поведение

- `/start` без параметров - главное меню «👋 Жэка Коммуналкин на связи». Без
  дома кнопки «🔎 Найти дом», «📝 Подать заявку», «📱 Открыть приложение»,
  с домом меню показывает адрес, а поиск становится кнопкой «🔎 Другой дом».
  Сотруднику УК меню напоминает, что кабинет УК - в приложении, и дает
  кнопку «🧑‍💼 Открыть кабинет УК».
- Без согласия на обработку данных бот показывает только экран согласия.
- `/help` - список команд.
- Смена статуса заявки сотрудником - сообщение жителю от бота.
- Нажатие на кнопку в старом сообщении - «🔄 Это окно устарело, открываю
  меню заново», и меню открывается.
- Недопустимое действие (например, чужая заявка) - короткое сообщение с
  причиной, диалог продолжается без перезапуска.
- Показание меньше предыдущего - предупреждение «Новое значение меньше
  предыдущего, уточните показание». Показание не за текущий период или за
  период с уже выставленной квитанцией - отказ с причиной.
- Без ключей Yandex распознавание возвращает пустое значение, а подсказка
  категории - `null`. Житель заполняет эти поля сам, и сценарий не
  прерывается.
- `GET /api/healthcheck` - 200, документация API - `/api/docs`.
- Новая заявка жителя - сообщение сотрудникам УК с кнопкой, открывающей
  заявку в кабинете. Автору заявки оно не приходит, даже если он сотрудник.
- Неожиданная ошибка в боте - «⚠️ Что-то пошло не так, попробуйте еще раз»,
  и меню открывается заново.
- Запрос к API без `initData` и без тестового токена - 401 с причиной.

## Проверка API

API мини-приложения - собственный API решения: `https://vkmax.k1rles.ru/api`,
контракт в `openapi.yaml` (OpenAPI 3.1), обязательные проверки в
`DATA-API.yaml`.

Мини-приложение авторизуется `initData` из MAX, которую нельзя получить вне
MAX и которая живет сутки. Поэтому для проверки есть тестовый токен
`34c63235dea4b1fb95ce89a9f108fc18` в заголовке `Authorization: Bearer <токен>`,
он же на служебном слайде презентации. Токен открывает одну учетную запись «Проверяющий API». Первые
две проверки в `DATA-API.yaml` дают ей согласие и демо-доступ, после этого у
нее есть квартира в демо-УК №5 и роль сотрудника этой УК. Ссылки со
служебного слайда ведут в демо-УК №1, поэтому заявки проверки не
пересекаются с заявками жюри. Обе проверки можно повторять. Другие
демо-УК и роль администратора токену закрыты: `/demo/activate` с ними
отвечает 403. Демо-УК №5 закрыта для всех, кроме токена, а сам токен не
активирует коды сотрудников, поэтому чужие действия не ломают проверки. Свои заявки токен ведет только до статуса «Принята»: на заявке
из `test_data` держится проверка `staff_status`, которая переводит ее в этот
статус. Засеянные заявки демо-УК №5 он ведет по всем статусам. Проверки
заявок передают `X-House-Id`: токен может привязаться и к другим домам, а без
заголовка житель нескольких домов получает 403.

```sh
TOKEN=34c63235dea4b1fb95ce89a9f108fc18
curl -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"version":"1.0"}' https://vkmax.k1rles.ru/api/me/consent
curl -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"number":5}' https://vkmax.k1rles.ru/api/demo/activate
curl -H "Authorization: Bearer $TOKEN" https://vkmax.k1rles.ru/api/me
```

Токен включает переменная `API_TEST_TOKEN`. Пустая переменная выключает
вход по токену. Значение выше действует на проде, локально токен - то, что
вписано в `.env`.

## Возможности MAX сверх минимума

Главная - **домовые чаты**: УК пишет жителям там, где они уже общаются. Бот
привязывается к чату дома, публикует в нем объявления из кабинета УК и
ведет список закрепов. Как проверить одним аккаунтом: получите роль
сотрудника по ссылке `demo_staff_1`, создайте в MAX группу и добавьте в нее
бота. Бот напишет в личку и спросит, к какому дому привязать чат, затем
попросит права администратора. После этого он поздоровается в чате с
кнопкой «🏠 Присоединиться к дому». Объявление из вкладки «Объявления»
кабинета УК придет в этот чат, а `/pin` в ответ на сообщение добавит его в
список закрепов.

Также:

- **Бот и мини-приложение связаны.** Уведомление о заявке и карточка
  приемки открывают заявку в приложении, сотруднику - в кабинете УК, а в
  меню бота у сотрудника есть кнопка «🧑‍💼 Открыть кабинет УК». Кнопка
  политики в согласии открывает политику. Ссылки `?start=` из QR,
  приглашений и демо-доступа сразу выбирают дом, организацию или роль.
- **Карточки в чате.** Приемка работы с фото, оценка и повторная заявка
  делаются прямо в чате с ботом. Исполнитель ведет заявку кнопками
  «🚗 Выехал» и «🏁 Готово» без мини-приложения и присылает фото результата,
  тогда в карточке приемки видно «было - стало». Карточки редактируются на
  месте, а не множатся.
- **QR на подъезде.** QR выдает администратор: получите роль по ссылке
  `demo_admin_1`, в кабинете УК откройте «Дома» - дом - QR. Ссылка из QR
  открывает бота с уже выбранным домом и подъездом.
- **Три уровня уведомлений** по категориям в профиле: со звуком, без звука,
  выключены. Статусы своих заявок выключить нельзя.

Карточку исполнителя проверить одним аккаунтом нельзя: исполнитель - это
отдельный участник УК. Для нее получите роль администратора по ссылке
`demo_admin_1`, в кабинете УК откройте «Дома» - «Организация и сотрудники»,
в блоке «Команда» пригласите второй аккаунт исполнителем и назначьте его на
принятую заявку в карточке заявки.

## Обращения и ПП РФ № 416

Работа с заявками сверена с Правилами управления МКД (ПП РФ от 15.05.2013
№ 416) в редакции от 20.06.2026:

- п. 35: обращение можно направить через MAX, официальный ответ идет тем же
  каналом. Заявку подают в боте или мини-приложении, смена статуса и ответ
  УК приходят жителю сообщением бота. Обращение по телефону сотрудник УК
  заводит заявкой сам, на прием житель записывается в мини-приложении.
- п. 36: на вопросы вне пунктов 31, 32 и 34 УК отвечает не позднее 10
  рабочих дней. Самый длинный срок категории заявки в Жэке - 72 часа.
- п. 34: сведения по общедомовым приборам учета и копии актов УК выдает не
  позднее 3 рабочих дней, срок 72 часа в них укладывается. Часть
  раскрываемой информации (УК и ее контакты, тарифы, капремонт, документы)
  житель видит в карточке дома без запроса.
- п. 38: запрос и ответ хранятся 3 года. Заявки и переписка по ним не
  удаляются.
- При подаче житель сразу получает номер заявки и срок, как п. 17.2 требует
  от аварийно-диспетчерской службы.

## Известные ограничения

- Сроки категорий заявок - ориентиры продукта, а не значения из ПП № 416.
  Пункт 13 требует локализовать аварию за 30 минут и устранить за 3 суток, а
  у протечки в Жэке один срок - 4 часа до выполнения. На вопрос о
  раскрываемой информации п. 34 требует ответить не позднее следующего дня,
  а у категории «Другое» срок 72 часа.
- HTTPS в репозитории не настроен: на проде TLS завершает nginx на хосте,
  перед compose.
- Интеграции с ГИС ЖКХ нет, начисления и оплата модельные. Для настоящих
  данных нужны выгрузка начислений из биллинга УК в таблицу `charges` и
  платежный шлюз УК (эквайринг или СБП). Для передачи показаний в ГИС ЖКХ
  нужен SOAP-обмен. Для него нужны электронная подпись УК и регистрация
  информационной системы в личном кабинете УК.
- Регистрация УК подтверждается только скрытым кодом: в настоящем продукте
  здесь нужна ЕСИА или письмо на официальный домен организации из реестра.
- Юридически значимое общее собрание собственников не проводится: опросы
  только помогают заранее собрать мнения.
- Бот не может написать жителю первым, если тот ни разу не открывал бота.
- Бот не создает домовые чаты сам: его добавляет в чат председатель или УК.
  По словам эксперта трека, список чатов бота в MAX хранит только последнюю
  тысячу чатов, поэтому привязанные домовые чаты бот берет из своей базы, а
  не из этого списка.
- MAX ограничивает бота 30 запросами в секунду: рассылка тысяче жителей
  занимает около 35 секунд.
- Демо-история заканчивается днем заполнения базы, через 30 дней дашборд
  пустеет.
- Кабинет УК не выгружает заявку документом, а в сообщениях для домовых
  чатов нет кнопки мини-приложения.
- Подсказки модели и распознавание фото ограничены 60 вызовами в час на
  пользователя. Счетчик живет в памяти процесса `api`: перезапуск его
  обнуляет, а каждый воркер gunicorn считает отдельно.
- Загрузка фото не ограничена квотой на пользователя, а неприкрепленные
  файлы не удаляются.

## Остановка и повторный запуск

```sh
docker compose stop             # остановить, контейнеры и данные остаются
docker compose start            # запустить остановленные контейнеры
docker compose down             # удалить контейнеры, база и Redis остаются в томах
docker compose up -d --build    # поднять заново, миграции прогонятся сами
docker compose down -v          # удалить и тома: база пустая, нужно заново заполнить
```

После `docker compose down -v` демо-данные нужно заполнить заново, как в
разделе «Тестовые данные». Фото в `backend/content` лежат на диске хоста и
вместе с томами не удаляются.
